Origin · 설계는 손으로, 구현만 에이전트에게
01 · 파이프라인 설계

완전히 맨땅에서 시작한 프로젝트였기 때문에, 초기에 체계를 잡는 것이 무엇보다 중요했습니다. 코드를 한 줄도 쓰기 전에 며칠 동안 직접 머릿속으로 대본 작성 → 발음 작성 → TTS → (애니메이션) 설계 → 씬 그리기 → 화면 캡처 검수 → 렌더로 이어지는 전체 파이프라인을 구상했습니다. 지금 위에 있는 파이프라인 표시는 그때 구상한 흐름이 실제로 구현된 결과입니다.

02 · 모듈 트리를 먼저 손으로

실제 코딩을 시작할 때도 Claude Code 같은 AI 도구의 도움은 받았지만, 디렉터리와 py 스크립트·md 프롬프트 파일들을 부서처럼 전부 모듈화해서 먼저 손으로 비워둔 뒤, 그 안을 채우는 코드 작성만 AI에게 맡겼습니다. 설계는 직접 하고 에이전트는 부하 코더로 활용한 구조입니다.

03 · 이렇게 한 이유

구조를 먼저 손으로 잡아두면, 프로젝트가 커질수록 에러가 났을 때 "어느 모듈의 문제인지"를 머릿속에서 먼저 좁힌 뒤 실제 조사에 들어갈 수 있어 디버깅 시간과 비용을 크게 아낄 수 있다고 판단했습니다. 실제로 그렇게 됐습니다 — 지금 이 프로젝트 하나가 app.py 4,211줄을 포함해 5개 LLM 프로바이더·3개 애니메이션 엔진을 오케스트레이션하는 규모로 커졌지만, 처음 잡아둔 모듈 경계가 그대로 유지되고 있습니다.

04 · 이 판단의 뿌리

이렇게 모듈 단위로 트리 구조를 먼저 설계해두는 습관은, 일본어 검수 작업을 하며 사내 번역 모듈 레포를 직접 클론해 모듈·스크립트·프롬프트 파일을 하나하나 열어보고 작동 방식을 머릿속에 담아뒀던 경험에서 왔습니다. 다른 사람이 만든 시스템의 구조를 뜯어봤던 경험이, 이 프로젝트를 처음부터 손으로 설계할 때 실질적인 기준점이 됐습니다.

Engineering Deep-Dive · 발음 정확도 파이프라인
01 · 문제

ElevenLabs로 한국어 내레이션을 처음 테스트했을 때 숫자와 영어 표기 두 지점에서 오류가 빈번했습니다. 고유어 숫자("다섯 개")와 한자어 숫자("오 초")를 문맥에 맞게 구분해 읽지 못했고, 영어 단어가 섞여 있으면 그 부분만 갑자기 원어민 발음으로 굴러가면서 목소리 톤과 억양 자체가 달라져 버렸습니다.

02 · 구조적 해결

화면 자막으로 노출되는 대본과는 별개로, TTS에만 입력되는 발음 전용 스크립트를 만드는 전처리 단계를 파이프라인에 추가했습니다(README의 Pronounce 단계). 화면에는 정상적인 문어체 대본이 뜨고, 실제 음성 합성에는 발음이 교정된 텍스트가 들어가는 구조입니다.

03 · 방법론 차용

이 문제를 풀 때, 한국어·일본어 콘텐츠를 검수하며 사내 번역 모듈(영→한, 한→일) 성능을 개선했던 경험에서 배운 방식을 그대로 가져왔습니다: 콘텐츠를 직접 읽으며 자연스러운 번역에 자주 실패하는 단어를 손으로 뽑아 glossary json을 만들고, LLM이 번역·발음 판단을 할 때 이 사전을 우선 참고하도록 만드는 방식입니다. 이 방식으로 SkillFit 한국어와 개발자 역량 검증 플랫폼 일본어 콘텐츠의 퀄리티를 실제로 끌어올린 경험이 있었고, 그 경험을 발음 문제에도 그대로 재적용했습니다.

04 · 발음 사전 직접 구축

API가 발음을 틀릴 때마다 손으로 발음 glossary에 항목을 추가하며 계속 누적 업데이트했습니다 (예: LLM → 에레렘, 5.0 → 오쩜녕). 영어 단어는 이 방식으로 대부분 커버됐지만, 숫자는 여전히 발음 판단에 실패하는 경우가 많았습니다 — 특히 "스무살", "스물한살" 같은 나이 표현에서 오류가 심했습니다.

이 항목 중 5.0 → 오쩜녕은 사실 표준 발음("오쩜영")과 다르게 일부러 틀리게 적어 넣은 항목입니다. 문법적으로는 "오쩜영"이 맞지만, 그대로 입력하면 TTS가 음절을 제대로 끊지 못하고 "오쩌명"처럼 뭉개서 발음했습니다. 국립국어원 규칙보다 실제 스피커에서 나오는 소리를 우선해, 규칙에는 어긋나도 TTS가 정확하게 발음해내는 표기를 직접 찾아 사전에 등록하는 시행착오를 항목마다 반복했습니다 — 언어학적으로 옳은 답과 엔진이 실제로 잘 읽는 답이 항상 같지는 않다는 것을 실전에서 계속 확인한 과정입니다.

05 · 규칙 기반 보강

남은 숫자 문제는 Python 정규식 전처리를 먼저 적용한 뒤, 그래도 LLM이 특히 헷갈려 하는 한국어 음운 규칙 — 비음화·유음화·구개음화·음절의 끝소리 규칙·된소리되기·니은첨가·사잇소리현상·거센소리되기 — 을 국립국어원 자료를 인용해 요약 문서화해서 함께 제공하는 방식으로 보강했습니다. 발음 문제를 사전 하나로 끝내지 않고, 사전(어휘 수준) + 정규식(패턴 수준) + 언어학 규칙 문서(원리 수준)를 층층이 쌓은 구조입니다.

기존에는 영상 전체를 하나의 HTML 파일로, 처음부터 끝까지 단일 에이전트가 순차 작성했습니다. 씬이 많아질수록 생성 시간이 선형으로 늘어났고, 무엇보다 중간에 실패해 폴백이 발생하면 그때까지 만든 작업 전체가 통째로 유실될 위험이 매우 컸습니다 — 영상 하나가 하나의 트랜잭션처럼 묶여 있었던 셈입니다. 이 구조를 2단계로 분리해 재설계했습니다: 먼저 Opus/Sonnet이 영상의 씬 구획(scene breakdown)만 설계하고, 그다음 각 씬의 실제 렌더링은 씬 개수만큼의 Fable/Opus 서브에이전트가 맡아 비동기 병렬로 동시에 작업합니다. 설계와 렌더링을 분리하고 렌더링 단위를 씬으로 쪼갠 덕분에 비용과 소요 시간을 현저히 줄였고, 실패가 나더라도 유실 범위가 영상 전체가 아닌 씬 하나로 좁혀졌습니다.

SkillFit — 텍스트 전용 콘텐츠에 인트로 영상 표준 배포

SkillFit은 원래 글로만 구성된 콘텐츠를 가진 학습 서비스였습니다. AI 인트로 영상 파이프라인을 SkillFit 콘텐츠 제작 흐름에 적용해, 각 학습 트랙의 각 단원마다 도입 영상을 제작해 본문 콘텐츠와 함께 배포하는 것을 표준 프로세스로 만들었습니다. 텍스트만 있던 학습 경험에 시각·청각적 도입부가 더해지면서 교육 콘텐츠 퀄리티가 올라갔고, 단원을 시작할 때 학습자가 느끼는 몰입도를 높이는 효과로 이어졌습니다.

외주 제작 비용을 없앤 자립형 사내 영상 제작 툴

이 프로젝트가 시작되기 전, SkillFit과 다른 회사 서비스가 소개·프로모션 영상이 필요할 때마다 매번 외주 제작사를 섭외해 견적을 받고, 시안을 컨펌하고, 수정 요청을 주고받는 과정을 반복해야 했습니다. 영상 한 편에 적지 않은 비용과 리드타임이 들었고, 사소한 문구 하나를 바꾸는 데도 외주사와의 커뮤니케이션 사이클을 다시 돌아야 하는 구조였습니다.

AI 인트로 영상 파이프라인을 개발자 전용 파이프라인 스크립트에서 멈추지 않고, 비개발자도 바로 쓸 수 있는 셀프서비스 웹 UI(스킬 파일·테마·보이스·영상 길이만 고르면 나머지는 자동으로 처리되는 간소화 페이지)까지 다듬은 이유가 여기에 있습니다. 스킬 JSON이나 마크다운 한 장만 있으면 대본 작성부터 TTS 내레이션, 애니메이션, 최종 영상 파일까지 전부 자동으로 만들어지기 때문에, 이제는 외주 제작사를 거치지 않고도 사내에서 영상을 자체적으로 완성할 수 있습니다. 결과적으로 지금은 운영팀이 SkillFit과 다른 여러 서비스의 소개 영상을 이 도구로 직접 제작하고 있습니다 — 엔지니어의 개입 없이도 기획부터 결과물 다운로드까지 운영팀이 스스로 완결할 수 있는 워크플로우가 사내에 자리잡은 것이 이 프로젝트가 만들어낸 가장 실질적인 변화입니다.

Research Rigor · Advisor / Worker 분리 실험
01 · 가설

mgs-video 파이프라인에서 씬 타이밍 설계와 QA 판정만 별도의 opus 서브에이전트(advisor)에게 위임하는 mgs-video-tiered 변형을 프로토타입으로 만들었습니다. "advisor를 추가로 부르면 실제로 씬-내레이션 탈싱크가 줄어드는가, 그 대가로 사용량이 얼마나 늘어나는가"를 감이 아니라 데이터로 검증하려는 목적이었습니다.

02 · 오염 발견

비교 실험을 진행하던 중, 기준으로 삼은 골든 예시 파일이 사실은 원본 실행 결과물의 사본이었고, 심지어 advisor에게 제공한 레시피 문서 자체에도 정답에 해당하는 스포일러가 섞여 있었다는 사실을 발견했습니다. advisor가 잘 맞힌 것처럼 보인 결과의 상당 부분이 실력이 아니라 오염된 입력 덕분이었을 수 있다는 뜻입니다. 결과를 조용히 폐기하는 대신, 보고서에 "이 표본은 순수하지 않다"고 그대로 명시했습니다.

03 · 재실행 설계

오염을 완전히 제거한 재실행을 별도로 설계했습니다. 격리된 서브에이전트에게는 스포일러를 제거한 정리된 자료만 제공하고, 매 단계마다 "본인이 실제로 어떤 파일을 열어봤는지"를 스스로 신고하게 만드는 절차까지 세워 재현했습니다(-tiered-clean 실행). 여기에 advisor 모델을 opus↔fable로 바꿔가며 정성 비교까지 추가로 진행해, 표본이 1회뿐이라는 한계를 스스로 명시하면서도 관찰 가능한 차이를 기록했습니다.

04 · 판단

그럼에도 "advisor를 추가하는 쪽이 명확히 더 낫다"고 확신할 수 있는 결과는 나오지 않았습니다. 애매한 결과를 억지로 성과처럼 포장하는 대신, 이 실험 스킬 자체를 프로젝트에서 삭제했습니다. 새로운 것을 만드는 것 못지않게, 이득이 불분명한 실험은 정리하는 판단도 스스로 내렸습니다.

이중 검수 체계와 피드백 환류 — 그리고 언어 장벽을 직접 넘은 과정
01 · 이중 검수 구조

검수를 두 단계로 나눠 운영했습니다. 1차 검수는 전문 번역가가 담당해 문법과 자연스러움 — AI 번역 티가 덜 나고 실제 현지인이 쓸 법한 표현인지 — 를 확인하고, 2차 검수는 일본에서 실제로 일하는 현지 개발자가 담당해 IT 콘텐츠에 등장하는 전문 용어가 현지 실무에서 통용되는 표현으로 로컬라이즈됐는지를 확인했습니다.

02 · 운영 사이클

배치마다 같은 사이클을 반복했습니다: 이번 샘플 배치 범위 확정 → 검수자분들과 메일로 단가 협의 → 외주용역계약서 작성 → 샘플 발송 → Notion에 직접 교정할 수 있는 작업 공간 마련. 계약·소통·작업 환경 세팅까지 검수 파이프라인의 운영 전 과정을 직접 챙겼습니다.

03 · 피드백 누적 → 표준 문서화

검수자들이 고쳐주신 내용을 전부 CSV로 모아 LLM에 누적 제공하면서, 반복적으로 지적되는 패턴을 뽑아냈습니다. 이렇게 정리한 것을 두 분의 일본어 번역 인사이트를 모은 규격 문서로 만들어 번역 모듈에 제공했고, 이는 번역 성능을 크게 개선하는 데 실제로 기여했습니다.

04 · 언어 장벽을 직접 넘은 과정

정작 본인은 히라가나·가타카나조차 모르는 상태로 이 검수 업무를 계속 맡아야 했고, 콘텐츠와 검수자 피드백을 이해하는 데 한계를 느꼈습니다. 이를 그대로 두지 않고 5월부터 직접 일본어 학습을 시작했습니다 — Duolingo와 Gemini로 문법을 익히고, J-pop으로 리듬을 붙이고, 랜덤 채팅으로 실제 일본인과 부딪히며 익혔습니다. 지금은 문장을 어느 정도 읽을 수 있는 수준이 됐습니다. 아직 다양한 한자를 다 외우지 못해 콘텐츠 속 IT 전문 용어를 직접 읽고 검수하는 것은 여전히 어렵지만, 콘텐츠에 반복적으로 등장하는 문장 구조나 검수자 인사이트 문서는 스스로 읽고 활용할 수 있게 되면서 검수 작업 자체가 한결 수월해졌습니다.
